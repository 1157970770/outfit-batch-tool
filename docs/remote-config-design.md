# 远程配置 + 授权：方案设计（先设计，未实施）

> 目标：把「RH Key、模板清单、COS、授权地址」全部放到云上，软件启动时自动拉取。
> 本地只保留一个内置的服务地址，使用者看不到、也改不了任何配置。
>
> 状态：**设计稿，等确认后再改代码。**

---

## 1. 要解决的问题

| 现状（v0.7） | 目标 |
| --- | --- |
| `配置.ini` 放在 exe 旁边，用户能看能改 | 取消 ini，配置全部远程下发 |
| RH Key 写在 ini 里，等于明文发给每个用户 | Key 不出服务器（推荐）或按 token 下发 |
| 换模板清单/COS/地址要重新打包 | 云端改一行，下次启动生效 |
| 用户可把 `LICENSE_SERVER` 改成自己的 | 只保留一个内置地址，改不了 |

---

## 2. 两条路线，先选一条

### 路线 A：配置下发（客户端仍直连 RunningHub）

```
启动 → POST /config {token} → 返回 {rh_key, manifest, cos, ...} → 客户端直连 RH
```

| 优点 | 缺点 |
| --- | --- |
| 改动小，现有代码基本不动 | **RH Key 必须发到客户端**，内存/抓包可提取 |
| 生成流量不经过你的服务器 | Key 泄露 = 所有人可白嫖 |
| 服务端几乎零负载 | 无法按用户限额、无法审计谁跑了多少 |

### 路线 B：中转代理（Key 只在服务器）★ 推荐

```
启动 → POST /activate {password, machine} → {token, config(不含 Key)}
生成 → POST /proxy/submit {token, body} → 服务器注入 Key → 转发 RH → 返回 taskId
轮询 → POST /proxy/query  {token, taskId} → 转发 RH /query
下载 → 直接下 RunningHub 的结果链接（不经过你）
```

| 优点 | 缺点 |
| --- | --- |
| **Key 永不落地**，客户端里没有 | 多一层转发，需处理超时/重试 |
| 可按密码限额（每人每天 N 条） | 服务端要扛 JSON 小包（几十 KB/次，不是视频流量） |
| 可审计、可封禁、可灰度 | 函数超时要调大（生成请求 5–30 秒返回） |
| 配置天然随 token 下发 | 实现量比 A 大（约 2–3 天） |

> 关键判断：RunningHub 的接口都是 **JSON 小包**（提交 <10 KB，轮询 <5 KB），视频是从它自己的 CDN 下载的。
> 所以"中转"不会产生视频带宽成本，只多几百毫秒延迟。

**建议 B**。如果暂时不想做代理，A 也能用，但必须接受"Key 迟早会泄露"。

## 3. 架构（按路线 B）

```
                    ┌──────────────── 云函数 outfit-license ────────────────┐
                    │                                                        │
 客户端 exe         │  POST /activate  密码+机器码 → token(14天) + config      │
   │                │  POST /verify    token → 是否有效（顺带续期/换配置）    │
   ├── 启动 ───────▶│  POST /proxy/submit  token 校验 → 注入 RH Key → 转发    │
   │                │  POST /proxy/query   token 校验 → 转发 /query          │
   ├── 生成 ───────▶│  GET  /health                                          │
   │                │                                                        │
   └── 下载 ◀───────┴── 直连 RunningHub 结果 URL（24h 内）                    │
                    └────────────────────────────────────────────────────────┘
                                     │
                          环境变量 / 云端配置表：
                          RH_API_KEY、MANIFEST_URL、COS_*、限额、版本
```

客户端内置**只有两项**：

```python
SERVICE_URL = "https://xxx.tencentscf.com"   # 配置/授权/代理三合一
```

连 `LICENSE_SERVER` 都不再单独存在。

## 4. 协议设计

### 4.1 `POST /activate`

```json
{ "action": "activate", "password": "RH-2026-001-xxxx", "machine": "880bad89..." }
```

```json
{
  "ok": true,
  "token": "eyJ...",
  "expire_at": 1798761600,
  "note": "张三 / 设计部",
  "config": {
    "manifest_url": "https://cdn.example.com/manifest.json",
    "cos": { "enabled": true, "bucket": "video-xxx-1463907213", "region": "ap-guangzhou", "prefix": "prod" },
    "quota": { "daily": 500, "used": 0 },
    "min_client_version": "0.8",
    "notice": "本周模板更新，建议重载"
  }
}
```

- `config` 里**没有 RH Key**（路线 B）。
- `quota` 让客户端显示"今日剩余 N 条"，服务端超限直接拒绝。

### 4.2 `POST /proxy/submit`

```json
{ "token": "eyJ...", "machine": "...", "body": { "prompt": "...", "imageUrls": ["..."], "videoUrls": ["..."] } }
```

服务端：验 token → 验配额 → 注入 `Authorization: Bearer <RH_KEY>` → 转发 → 回 `{ok, taskId, status}`。
**客户端永远拿不到 Key，也改不了 Key。**

### 4.3 `POST /proxy/query`

```json
{ "token": "...", "taskId": "2013508786110730241" }
```
→ 原样转发 `/query` 的响应（含 `results[].url`）。

### 4.4 错误码

| HTTP | error | 客户端行为 |
| --- | --- | --- |
| 401 | 密码不存在 / 已到期 / 已停用 | 弹框，重输 |
| 403 | 配额已用完（今日 500 条） | 提示明天再来 |
| 403 | 客户端版本过低（< min_client_version） | 提示下载新版本 |
| 409 | 该密码已在另一台机器激活 | 提示联系管理员 |
| 503 | 上游 RH 暂时不可用 | 自动重试 2 次 |

## 5. 启动流程（时序）

```
① 读内置 SERVICE_URL（常量，改不了）
② 读本地缓存 ticket.json（机器码 + token + 上次 config + 上次核验时间）
③ 有票且未过期 → POST /verify
      ├─ ok      → 用返回的 config 刷新本地缓存 → 进主界面
      ├─ 401/403 → 清票 → 弹密码框
      └─ 网络失败 → 7 天宽限内放行（用缓存 config），超过则要求联网
④ 无票 → 弹密码框 → /activate → 存票 + config → 进主界面
⑤ 进主界面后：后台静默拉一次 config（换模板不用重启）
```

**失败关闭**：拿不到 config 且本地无缓存 → 拒绝启动，提示"无法连接配置服务"。

## 6. 本地还留什么

| 项 | 位置 | 谁可改 |
| --- | --- | --- |
| 授权票 + 配置缓存 | `%APPDATA%\RHOutfitTool\ticket.json` | 程序自动维护，不面向用户 |
| 输出目录 | 同目录 `ui.json`，或下次启动沿用上次选择 | **用户通过"浏览"选择** |
| 提示词 | 界面上可改，随批次存 `batch.json` | 用户 |
| 服装图 | 用户每次选 | 用户 |

界面上**没有**任何输入框用于 Key/清单/COS/地址——只在状态条显示"已就绪/授权至 X/配额剩余 N"。

## 7. 安全设计

| 风险 | 对策 |
| --- | --- |
| Key 泄露 | 路线 B 下 Key 不出服务器；日志里打码 |
| 抓包重放 | token 绑机器码 + 短有效期（14 天）；代理接口全部校验 token |
| 篡改客户端跳过校验 | 无解，只能提高成本；定位仍是"防随手转发" |
| 服务端被刷 | 密码级配额 + 每 IP 频率限制 + 云函数并发上限 |
| 配置被中间人改 | 全站 HTTPS；config 带 `sig`（可选，HMAC 签名） |
| 服务挂掉全员不能干活 | config 本地缓存 + 7 天宽限；代理接口失败时提示而不是崩溃 |

## 8. 迁移步骤（分三期，每期都能单独上线）

| 期 | 内容 | 影响 | 预估 |
| --- | --- | --- | --- |
| **一期** | 服务端加 `/config`（返回 manifest/COS/配额）；客户端去掉 ini，改为拉取 | 界面少两个按钮；RH Key 仍在客户端 | 半天 |
| **二期** | 加 `/proxy/submit` `/proxy/query`；客户端改走代理 | Key 从客户端消失 | 1–2 天 |
| **三期** | 配额统计、版本门槛、后台通知、管理页 | 纯服务端 + 少量 UI | 1 天 |

三期做完，客户端里只剩：内置服务地址 + 界面状态。

## 9. 需要你确认的三件事

| # | 问题 | 选项 |
| --- | --- | --- |
| 1 | RH Key 是否允许下发到客户端？ | A 下发（快，但有泄露风险）／**B 不下发、走代理（推荐）** |
| 2 | 要不要按用户限额（每人每天 N 条）？ | 要／不要（不做的话没法防一个人刷光余额） |
| 3 | 配置改了要"下次启动生效"还是"立即生效"？ | 下次启动（简单）／立即（客户端定时拉，多几次请求） |
