## 1. 修的两件事

### P0-1 单条异常会带死整条调度线

`JobManager._dispatch` 是全站唯一一条派发线程，循环体没有异常保护：

- `app/web/jobs.py` 的 `_load_jobs` 用 `job.get("id", path.stem)` 当键，却**不把 `id` 补回字段**；
- 派发时 `self.active[job["id"]] = ...` 对这类 job 直接 `KeyError`；
- 线程资源紧张时 `Thread.start()` 抛 `RuntimeError`（且此时 `active` 已被写入，槽位泄漏）；
- 两种异常都会逃出 `while` 循环 → 派发线程静默死亡。表现为：新任务能提交、前端显示「已排队」，但再没有人派发，全站任务永久排队，直到重启服务。

### P0-2 「5 成功 + 5 无效」被报成「全部完成」

引擎 `summary` 只统计 `status == "failed"`，而 `_run_one` 还会产出 `invalid / expired / canceled / skipped / running` 五种非成功状态。下游 `_run_job` 只看 `success`/`failed`：

- `success 5 + invalid 5` → 走 `elif summary["success"]` 分支 → `succeeded` + 「全部完成。」；
- `job["done"]` 直接取 `summary["total"]`，进度条拉满 100%；
- `retry_failed` 认 `{"failed","invalid","expired","canceled"}`，但任务状态是 `succeeded`，进去先撞「任务尚未结束，暂时不能重试」。

## 3. 行为变化（用户/接口可见）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 老 job 文件缺 `id` | 派发 `KeyError`，全站排队停摆 | 载入时补 `id` 并回写；派发正常 |
| 起线程失败 | 槽位泄漏 + 后续 job 全部卡住 | 只该 job `failed`（消息含原因），其余照常派发 |
| 建输出目录抛 `OSError` | 永卡 `running`、槽位不释放、不可重试 | 落 `failed` + 消息，`active` 释放，可重试 |
| 排队期取消 | `_run_job` 仍改回 `running` 跑完整批 | 检测到取消即返回，状态保持 `canceled` |
| 10 条里 5 成功 5 无效 | `succeeded` + 「全部完成。」+ 100% | `partial` + 「成功 5/10，另有 5 条未成功（失败/无效/超时/取消/跳过）」+ 进度 10/10 |
| 等待超时的条目 | `done` 拉满，任务显示完成 | `done = total − running`，进度不满；重试时提示「还有条目在等云端出片」 |
| 只有 `skipped` 条目 | 不可重试 | 可重试 |
| 事件回调晚于 job 清理 | `KeyError` 打断整批回调 | 静默返回 |

## 4. 测试

新增 `tests/test_jobs_state.py`，6 组断言：

1. `_load_jobs` 按文件名补 `id`，且磁盘文件被回写；
2. `_spawn` 抛 `RuntimeError` 后该 job 判 `failed`、`active` 清空，**且后续 job 仍被派发**；
3. 无 `id` 的 job 就地失败，不阻塞后面的 job；
4. `unique_batch_dir` 抛 `OSError` 时状态落终态、`active` 释放、失败已落盘；
5. `_job_outcome` 四种映射（含「5 成功 + 5 invalid → partial 且 done=10」「running 不满进度」「空批次按失败」）与 `_finish_job` 的取消优先口径；
6. `status_counts` 覆盖全部状态 + 「9 条里 7 条未成功 → partial」的组合断言。

**全量结果**：`通过 13 / 13，跳过 0，失败 0`（含 `test_web`、`test_batches` 端到端）。
