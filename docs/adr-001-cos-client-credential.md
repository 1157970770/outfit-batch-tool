# ADR-001：客户端持有 COS 子账号密钥（接受风险，暂不改架构）

**状态**：已接受　**日期**：2026-10-26　**决策人**：项目负责人
**相关**：[license-integration.md](license-integration.md) §10

---

## 1. 背景

成品视频需要自动归档到 COS（`video-output-1463907213/prod/output/`）。归档由客户端直接上传，
所以客户端必须能对 COS 发起写请求。

当前做法：服务端把一组**专用子账号密钥**随 `/activate`、`/verify` 下发给客户端，客户端用 DPAPI 加密后存在
`%APPDATA%\RHOutfitTool\license.json`，运行时解密后交给 `qcloud_cos` SDK 使用。

这带来一个已知问题：**密钥实际上落在客户机磁盘上**，只要拿到那台机器 + 一个有效密码，就能解出来。

## 2. 风险（写清楚，避免以后误判）

| # | 事实 | 说明 |
| --- | --- | --- |
| R1 | **反编译 exe 拿不到密钥** | 密钥不在代码里，是服务端运行时下发的 |
| R2 | **但有密码 + 一台机器就能解出来** | DPAPI 只绑定 Windows 用户，同用户下任何进程都能 `CryptUnprotectData`。真实门槛是"一个有效密码 + 一台已激活的机器" |
| R3 | **DPAPI 不是安全边界** | 它防的是"文件被单独拷走/换台机器用"；防不了"在本机被读"。等价于一个带混淆的明文文件 |
| R4 | **离线宽限期会让旧密钥多活 7 天** | 客户端连不上授权服务时按上次核验放行，期间 `config` 不刷新 |
| R5 | **密钥随分发包扩散** | 一旦泄露，只能靠轮换或禁用收口，不能"召回" |

### 但暴露面被压得很小（这是"接受"成立的前提）

以下边界**实测过**（不是设计意图）：

| 能力 | 结果 |
| --- | --- |
| `PutObject` / `GetObject` / 四个分片动作 | ✅ 仅 `video-output-1463907213/prod/output/*` |
| 列举桶（`GetBucket`） | ❌ `AccessDenied` |
| 删除对象 | ❌ 无权限 |
| 访问 `video-input-1463907213`（模板桶） | ❌ 完全无权限 |

结论：拿到密钥的人**最多能往成品区写垃圾或覆盖自己的成品**——不能读模板素材、不能删数据、不能遍历桶。
最坏情况是"成品可被破坏"，不是"素材外泄"或"桶被接管"。

## 3. 决策

**保持现状，不改造。**

理由：

1. 项目是**公司内部工具**，使用者是已知的少数内部人员，风险模型可控。
2. 改造（服务端预签名 / STS）需要改服务端 + 改客户端 + 重新打包 + 灰度，收益是"去掉客户端密钥"——
   对内部场景不划算。
3. 真正的兜底手段已经具备：密码可 `revoke`（立刻拒绝）、密钥可轮换（一次 deploy，不重打包）。

## 4. 已做的缓解（持续有效）

| 措施 | 状态 |
| --- | --- |
| 专用子账号，最小权限（仅成品区 Put/Get/分片） | ✅ 已配并实测 |
| 密码 `revoke` 即时生效（`/verify` 每次回表复查） | ✅ 已实现 |
| 密钥轮换不需重打包（改 `config.json` + deploy，客户端下次启动自动换） | ✅ 已实现 |
| 成品按 `prod/output/<日期>/<批次>/` 分区，异常可定位 | ✅ 已实现 |
| 子账号无控制台登录权限 | ✅ 已配 |

## 5. 明确不做（以及接受的后果）

| 不做 | 接受的后果 |
| --- | --- |
| 不做服务端预签名上传 | 密钥长期存在于客户机 |
| 不做 STS 临时凭证 | 同上，且没有 2 小时自然过期 |
| 不切断 `~/.cos/credentials.json` / `~/.tccli` 本机凭证回退 | 若客户机恰好配了管理员凭证，客户端可能用更高权限上传（内部机器通常没有） |

## 6. 什么时候要重新评估（照表判断，别靠感觉）

| 触发条件 | 为什么 |
| --- | --- |
| 客户端要发给**非内部人员**（外部客户、外包、试用） | 风险模型从"可信内部"变成"不可控外部" |
| 成品区出现**异常写入**（对象数/体积突增、陌生来源 IP） | 可能已泄露 |
| 需要**对外演示**同一套生产环境 | 演示机不该持有能写生产桶的密钥 |
| **人员变动 / 离职** | 配合密码 `revoke`，必要时同时轮换密钥 |
| 开始有**对外计费或合规**要求 | 需要可审计的凭证链 |

## 7. 如果将来要改（方案已设计，勿重做）

| 路径 | 一句话 | 代价 |
| --- | --- | --- |
| **服务端预签名**（推荐） | 客户端零密钥，向云函数要 15–30 分钟的 PUT/GET URL；服务端手写 HMAC-SHA1，零第三方依赖（SCF 128MB/5s 足够） | 服务端 +180 行、客户端新增 `RemoteStorage`、必须重新打包 |
| STS 临时凭证 | 服务端 AssumeRole 发 2 小时凭证，客户端用 SDK + `Token` 字段 | 新增 CAM 角色 + 客户端刷新逻辑 |
| 取消客户端归档 | `cos.enabled=false`，归档交给有凭证的机器跑 `scripts/archive_to_cos.py` | 零代码改动，失去自动上云 |

**无论选哪条都要先记住这个坑**：预签名 URL 的权限 = **签名者密钥**的权限。
现有 `rh-client-uploader` 只能写 output 桶、**完全不能读 input 桶**，拿它去签模板 GET 会 403。
所以要改就必须新建服务端专用子账号（写 output + 读 `input/tpl`），并把密钥留在服务端、永不下发。

## 附：验证"密钥到底能干什么"的最小方法

```bash
# 用下发的密钥跑一次边界探针（脚本在 tools/ 下，按需临时写）
PUT  video-output/prod/output/_probe.txt   → 期望 200
GET  video-output/prod/output/_probe.txt   → 期望 200
PUT  video-input/prod/output/_probe.txt    → 期望 403
LIST video-output                          → 期望 403
```
