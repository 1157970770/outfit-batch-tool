## 1. P1 五连修

### 1.1 金额字段按角色裁剪（P1-5）

违反硬约束 5：金额只应走 `/api/admin/usage` 与 `/api/admin/accounts/<owner>/work`，
但任务轮询（3.5s 一次）和批次候选/生产/详情都在给普通用户回单价与金额，
F12 就能反推 `wan.price_per_second`。

| 位置 | 改法 |
| --- | --- |
| `jobs.py public(job, admin=False)` | 非 admin：summary 剥 `billable_seconds/estimated_cost/cost`（`_MONEY_KEYS`），records 白名单剥同样字段；admin 原样 |
| `jobs.py` 调用链 | `get()/list_for()/create()/retry_failed()` 全部加 `admin` 参数并透传；`server.py` 的 create/retry/detail/authorized 四处传 `user.get("role") == "admin"` |
| `batches.py _money_view(user, estimate)` | 非 admin 剥 `unit_price/price_source/amount`，**但保留 `options[].count`**——前端生产按钮的档位靠它（batch.js:84），只剥 `options[].amount` |

行为变化：普通用户在浏览器 F12 里再也看不到任何金额；管理端所有金额接口不变。

### 1.2 等待超时落终态 `timeout`（P1-19）

原来 `except WaitTimeout` 把记录写成 `"running"`——非终态：永久不可重试
（重试白名单只收 failed/invalid/expired/canceled/skipped）、永久计入「进行中」，
而云端大概率已出片并计费。

- `core.py`：`WaitTimeout` → `rec["status"] = "timeout"`，保留 `task_id` 供控制台核对。
- `core.py status_counts`：分列加 `timeout`。
- `jobs.py _RETRYABLE_RECORD_STATES`：加 `timeout`；文案「或等待超时」从 running 提示里移除。
- 前端 `app.js`：状态表加 `timeout: '等待超时'`；失败计数（决定重试按钮）补 `timeout/skipped`。

### 1.3 重试归属修正（P1-20）

原来 `retry_failed(job_id, owner)` 用**当前登录用户**建新 job：管理员重试他人任务，
用量/金额记到管理员头上，原主看不到结果；且 `batch_ref=""`，批次历史回查断链。

现在：`create(str(source.get("owner") or owner), ..., batch_ref=str(source.get("batch_ref") or ""))`。
权限判断仍在 server 层（`_authorized_job`），管理语义不变。

### 1.4 EXIF 方向 + 解压炸弹守卫（P1-21）

手机竖拍图带 EXIF Orientation=6，`Image.open` 读到的 `size` 是横躺的：
校验按横的放过、上传后模型侧构图错乱且照常计费。

- `media.py` 新增 `MAX_IMAGE_PIXELS = 64_000_000`（8000×8000，官方单边上限），
  并设 `Image.MAX_IMAGE_PIXELS` 收紧 Pillow 默认阈值；`DecompressionBombError`
  转成友好 `MediaError`。
- `inspect_image`：读 `orientation`（EXIF 274），**校验尺寸一律用
  `ImageOps.exif_transpose` 转正后**的宽高。
- `_flatten_to_jpeg`：转码前先 `exif_transpose`。
- `prepare_image`：orientation ∉ {0, 1} 的图即使 RGB JPEG 也走转码（透传不保证模型认 EXIF）。
- 顺带（P2）：`validate_video` 对「ffprobe 正常跑但解不出容器」直接拒绝——
  `.txt` 改名 `.mp4` 不再漏过；ffprobe 缺失的机器仍只告警放行。

### 1.5 COS REST 临时凭证带安全令牌（P1-22）

`CosRestClient` 没有 `token` 参数也没有 `x-cos-security-token` 头，
`~/.tccli` 临时凭证（STS）一用就全量 403，报错还不提示缺令牌。

- `CosRestClient.__init__(..., token="")`；新增 `_headers(method, key, extra, params)`
  统一拼头：有 token 就带 `x-cos-security-token`。
- PUT/打标签/DELETE 走请求头；列举（query 签名）与 `sign_url` 把令牌作为
  query 参数携带——两种签名路径都覆盖。
- `CosRestStorage.__init__` 传入 `cfg.token`（与 SDK 路径 `Token=...` 对齐）。
- 网络动作统一包 `_with_retry`（从 storage.py 复用，指数退避），与 SDK 路径一致；
  `_range_stat` 不包——它的 404→None 语义会被 `_with_retry` 破坏。

### 1.6 前端：pending 同步 + 上传超时（P1-23 / P1-24）

**P1-23**：四个批量按钮（全选本页/反选/全选全部/清空）只改 `selected` 不重置 `pending`。
路径「点开任意一条 → 全选全部 → 保存」会把那条的标签**追加给全库**（N 可达数千）。

- 新增 `setSelection(nextIds)`：0 条取预览行标签、1 条取该行标签、≥2 条清空；
  mode 只在「单条 ↔ 批量」边界切换（`lastMulti` 跟踪），不覆盖用户手动选择。
- 行勾选框与四个批量按钮全部改走它；预览行点击同步 `lastMulti`。

**P1-24**：上传 XHR 没有超时——连接挂起时 onload/onerror 都不触发，
Promise 永不 resolve，`busy` 永久 true，弹窗关不掉。

- `xhr.timeout = 120000` + `ontimeout` 置失败并 resolve；
- `startUpload` 的 `try/finally` 无条件清 `busy`；
- 失败项（含超时）可再点「开始上传」重试（队列快照，不会本轮内自动重试）。

## 3. 失败口径恒等式（本轮新发现，随批修掉）

盘点时发现 `usage_for` / `work_for` 口径不一致：`skipped` 在账户汇总里既不进
success 也不进 failed/unfinished，`work_for` 连 `unknown` 都不算——
`items ≠ success + failed + unfinished`，管理端汇总页与明细页对不上。

现在统一走 `jobs.py _FAILED_RECORD_STATES = {failed, invalid, expired, canceled,
unknown, timeout, skipped}`；`work_for` 的 unfinished 改成 else 兜底
（非成功非失败即进行中），恒等式对新状态恒成立。测试断言两侧一致。
