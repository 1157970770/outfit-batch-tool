# 单 Key 共用 · 账户用量监控

- 版本：网页端 v0.6.0（2026-11-02）
- 现状：**全站 1 把 API Key，所有账户共用**；存在单人一次跑 50 条，不存在多账户同时各跑 50 条。
- 目标：管理员能按账户看清「谁跑了哪些视频、花了多少钱」。

---

## 一、结论先行

| 项 | 现在 |
|---|---|
| API Key | 1 把，写在 `server/config.json` 的 `wan.api_key`，所有账户共用 |
| 额度 | 两个独立桶：创建任务 250 RPM（官方 300）、轮询 15 RPS（官方 20）；在飞 100，另给小批量 12 |
| 归属 | 按 `job.owner` 记账，与 Key 无关 |
| 监控 | 管理 → 账户用量 → 点账户看逐条明细，可筛选、导出 CSV |
| 已移除 | `server/keys.json`、独立 Key、共用开关、缺 Key 阻断等一整套多 Key 代码 |

**额度含义**：单人跑 50 条用不满 100 个在飞；两个人各 50 条正好占满，可以同时跑；第三个人会等名额释放。
官方额度按 Key 计，一把 Key 只有一份，拆账户不会多出额度。

---

## 二、监控怎么用

1. 管理 → 「账户用量」：每账户一行，任务数、条数、成功/失败、计费秒、预估金额、最近活跃。
2. **点账户名** → 展开「工作明细」：时间、批次号、视频名称+模板 ID、状态、计费秒、金额。
3. 可按起止日期、状态筛选；「导出 CSV」给出当前筛选条件下的全量明细
   （带 BOM，Excel 直接打开不乱码）。
4. 合计行是**筛选结果全量**的合计，不是当前页。

金额算法：`计费秒 × 单价`。计费秒来自云端 `usage`（输入时长 + 输出时长）；单价取
`wan.price_per_second`，为 null 时用公开价目表兜底（480P 0.3 / 720P 0.6 / 1080P 1.2 元/秒）。
**这是估算，真实账单以阿里云为准。**

> 金额只在管理端出现：小批量试跑、大批量生产、历史任务等**非管理员页面不显示任何金额或费用提示**，
> 生产按钮只标条数（`生产 50 条`）。要看花销，统一走「管理 → 账户用量」。

> 历史任务在单价还是 null 时生成，记录里没有金额；读取时按**当前**单价回算，
> 明细标记 `cost_source=derived`，CSV 的「金额来源」列区分「实测 / 按当前单价回算」。
> 回算只发生在读取时，不修改任务文件。

## 三、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/usage?from=&to=&owner=` | 按账户聚合 |
| GET | `/api/admin/accounts/{账户}/work?from=&to=&status=&offset=&limit=` | 逐条明细（分页） |
| GET | `/api/admin/accounts/{账户}/work.csv?from=&to=&status=` | 明细 CSV |
| GET | `/api/jobs?scope=all&owner=` | 管理员按账户筛选任务 |
| GET | `/api/batches?scope=all&owner=` | 管理员按账户筛选批次 |
| GET | `/api/history/groups?scope=all&owner=` | 管理员按账户筛选历史分组 |

普通账号的接口始终只返回自己的数据；`scope=all` 与 `owner` 只对管理员生效。

## 四、配置与限制

| 配置 | 位置 | 当前值 | 说明 |
|---|---|---|---|
| `wan.api_key` | `server/config.json` | 已有 | 全站唯一 Key，缺了服务直接启动失败 |
| `wan.price_per_second` | 同上 | 三档 null | 建议填实际合同价，金额才和账单对得上 |
| `max_active_jobs` | `server/web.json` | **4** | 同时跑几个**大批量** job；小批量另算 |
| `max_active_per_user` | 同上 | 1 | 每账户同时几个大批量 job；小批量可并行 |
| `small_lane_items` | 同上 | **3** | 条数 ≤ 该值走快速通道 |
| `max_active_small_jobs` | 同上 | **4** | 快速通道同时跑几个小 job |
| `small_lane_inflight` | 同上 | **12** | 快速通道专用在飞名额（独立池） |
| `wan.max_concurrency` | `server/config.json` | **100** | 单 job 线程数（上限也从 50 提到 100） |
| `wan.poll_interval` | 同上 | **15** | 轮询间隔；受轮询 RPS 约束，见下 |
| `wan.max_inflight` | 同上 | **100** | 全站同时在飞任务数 |
| `wan.query_rpm` | 同上 | **250** | **创建任务**的每分钟请求数（官方 300） |
| `wan.query_rps` | 同上 | **15** | **轮询**的每秒请求数（官方 20） |

### 创建与轮询是两个额度

官方对 `wan3.0-video` 的口径是分开的：

- 创建任务：**300 RPM**；
- 轮询结果：**20 RPS**（约 1200 次/分），不是 300 RPM 的一部分。

旧实现把两者塞进同一个 250 RPM 桶，等于把轮询也限死在 4.2 次/秒，白白拖慢进度。
v0.6.0 起拆成两个独立令牌桶：

```
提交桶：250 RPM（0.24 秒/次）  → POST /video-synthesis
轮询桶：15 RPS（0.067 秒/次）  → GET /tasks/{id}
```

轮询占用只取决于在飞数 N 和间隔 T：

| 在飞 N | 间隔 T | 轮询速率 | 15 RPS 是否够 |
|---|---|---|---|
| 100 | 15s | 6.7 RPS | 够（45%） |
| 200 | 15s | 13.3 RPS | 够（89%） |
| **100** | **10s** | **10 RPS** | 够（67%） |
| 400 | 15s | 26.7 RPS | 不够，需拉长到 30s |

所以当前 100 在飞、15 秒轮询只用了官方轮询额度的三分之一，不需要再靠拉长间隔省请求。
提交桶与轮询桶互不挤占：50 条创建不会吃掉轮询预算，轮询也不会拖延新任务提交。

> 注意：如果阿里云实际把两个接口合并计入 300 RPM（与官方说明不符），15 RPS 轮询会超。
> 上线后观察日志里的 `[限流]`；一旦出现，把 `query_rps` 降到 5 再试。

### 快速通道（≤3 条）

工作场景里一个人可能一边跑大批量、一边想试 1–3 条新提示词。这两件事之前会互相卡：

| 层 | 大批量 | 快速通道（≤3 条） |
|---|---|---|
| job 槽位 | `max_active_jobs=4` | 独立 4 个，不占大批量槽位 |
| 每用户 job 数 | `max_active_per_user=1` | 每人额外 1 个，可与本人大批量并行 |
| 在飞名额 | 100（主池） | **独立 12 个**，不跟大批量抢 |
| 调度顺序 | 按提交时间 | **优先放行**，即使晚提交 |

- 判定只看条数：`len(templates) <= small_lane_items`，与来源页面无关；
- 最坏请求量：100 大批量 + 12 小批量 = 112 条在飞，30 秒轮询 224 次/分，加提交约 14 次/分，
  合计约 238 / 250，仍在预算内；
- 线程：4 个大 job（各 50 条）+ 4 个小 job ≈ 212 线程；若大 job 都是 100 条则约 412，属可接受范围。

- **时间口径**：按任务创建时间（`created_at`）归档；跨月才跑完的任务算在创建月。
- **失败不计费**：failed / invalid / expired / canceled 不计费，金额为空。
- **控制台对账**：1 把 Key 时控制台只有一个总额，本地台账按账户拆分；差异主要来自单价估算。
- **手机/局域网**：4 个账户共用一个桶，别在高峰期同时提交大批次。

## 五、变更记录

- **v0.6.0（2026-11-02）**：按官方口径拆开「创建任务 300 RPM」与「轮询 20 RPS」两个额度，
  提交/轮询各用一个令牌桶；轮询间隔从 30 秒恢复到 15 秒，进度更新更快，且不再挤占提交预算。
- **v0.5.0（2026-11-02）**：新增「快速通道」——≤3 条的小批量拥有独立 job 槽位与 12 个在飞名额，
  可与本人的大批量并行，并在调度时优先放行；任务列表显示「快速通道」标记。
- **v0.4.0（2026-11-02）**：按实际使用形态收敛为「单 Key 共用」。移除 `app/web/keys.py`、
  `keys.json`、账户级 Key 接口与管理页 Key 卡片、按 Key 分桶的限流；限流与在飞恢复为进程级单例。
  保留并强化账户监控：用量聚合、逐条明细、CSV、按账户筛选。
- **v0.3.0（2026-10-31）**：支持共用主 Key 与独立 Key 两种模式，新增逐条明细。
- **v0.2.0（2026-10-31）**：引入账户级 Key 与按 Key 分桶（已被 v0.4.0 移除）。
