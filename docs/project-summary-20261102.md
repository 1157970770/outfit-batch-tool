# 换装批量生产器 · 项目现状总结

- 日期：2026-11-02
- 版本：网页端 **v0.6.0**
- 适用范围：局域网内部工具（5–10 人），单机部署，浏览器访问
- 关联文档：`web-lan.md`（部署）、`account-usage-and-quota.md`（账户与额度）

> 一句话：**1 把阿里云 Key 支撑多账户的换装视频批量生产，按账户记账，创建/轮询双额度，大小批量双通道。**

## 2. 系统结构

```
浏览器（原生 JS）
   │  HTTP / Cookie 会话
   ▼
app/web/server.py  ThreadingHTTPServer
   ├─ auth.py        密码、会话、登录限流
   ├─ jobs.py        任务队列、调度、账户统计
   ├─ batches.py     批次实体、候选、锁定、分批生产
   ├─ templates.py   模板目录 + 标签工作簿
   └─ settings.py    配置装载
          │
          ▼
app/core.py  BatchRunner（线程池 + 在飞闸门）
          │
          ▼
app/wan_api.py  百炼 DashScope / RunningHub 适配
   ├─ 提交桶（RPM）  ── POST /video-synthesis
   └─ 轮询桶（RPS）  ── GET /tasks/{id}
```

存储分两处：模板与成片走腾讯云 COS，任务/批次/日志/上传图落在本机 `web-data/`。

## 4. API Key 与额度模型

### 4.1 单 Key 共用

全站只有一把 Key，写在 `server/config.json` 的 `wan.api_key`，所有账户共用。**没有 `keys.json`、没有独立 Key、没有缺 Key 阻断**（多 Key 相关代码已于 v0.4.0 移除）。

归属与 Key 无关：哪条视频算谁的，只看 `job.owner`；Key 只决定额度。

### 4.2 两个独立额度

官方对 `wan3.0-video` 的口径是分开的：

| 接口                           | 官方限制    | 本系统取值            | 实际间隔      |
| ---------------------------- | ------- | ---------------- | --------- |
| 创建任务 `POST /video-synthesis` | 300 RPM | **250 RPM**（83%） | 0.24 秒/次  |
| 轮询结果 `GET /tasks/{id}`       | 20 RPS  | **15 RPS**（75%）  | 0.067 秒/次 |

两个令牌桶互相独立：提交 50 条不会吃掉轮询预算，轮询也不会拖延新任务提交。命中 429 时，惩罚只落到对应接口的桶上。

### 4.3 在飞名额

| 池     | 大小      | 用途            |
| ----- | ------- | ------------- |
| 大批量主池 | **100** | 普通任务，跨账户共享    |
| 快速通道池 | **12**  | ≤3 条的小批量，独立预留 |

在飞 = 已提交、尚未终态的任务，覆盖 `submit → wait` 全程；任务结束才释放名额。

当前 100 条在飞、15 秒轮询：

```
轮询  100 ÷ 15 = 6.7 RPS（官方 20 的 33%）
提交  突发：100 条 × 0.24 秒 = 24 秒内发完，瞬时 250 次/分（配额 100%）
      稳态：12.5 次/分（= 100 在飞 ÷ 8 分钟）
```

> **别把 12.5 次/分当成限速**：提交能力上限是 250 次/分（4.17 次/秒），12.5 是
> 「100 条在飞、单条 8 分钟」条件下的**吞吐**——名额 8 分钟才轮换一遍，提交自然只能跟上这个节奏。
> 它占配额的 5%，说明提交完全不是瓶颈，剩余 95% 用于突发提交、重试和多人同时起批。
> 想把吞吐提上去，要加在飞数（`wan.max_inflight`），不是提高提交速率。

## 5. 快速通道（≤3 条）

工作场景里，一个人可能一边跑大批量、一边试 1–3 条新提示词。快速通道保证小批量不被大批量排队卡住。

| 层         | 大批量                 | 快速通道             |
| --------- | ------------------- | ---------------- |
| 判定        | 条数 > 3              | 条数 ≤ 3           |
| job 槽位    | `max_active_jobs=4` | 独立 4 个，不占大批量槽位   |
| 每用户 job 数 | 1                   | 额外 1 个，可与本人大批量并行 |
| 在飞名额      | 主池 100              | 独立池 12           |
| 调度顺序      | 按提交时间               | 优先放行             |

最坏请求量：100 大批量 + 12 小批量 = 112 条在飞，15 秒轮询约 7.5 RPS，仍在 15 RPS 内。

## 7. 生产流程

### 7.1 小批量试跑

- 单次最多 3 条，用于验证素材、标签、提示词；
- ≤3 条自动走快速通道；
- 输出时长默认 7 秒，可选跟随场景。

### 7.2 大批量生产

1. 新建批次：批次号（忽略大小写唯一）、定妆图、提示词、筛选条件；
2. 逐条预览并勾选，锁定清单（`draft → locked`）；
3. 按 20 / 50 / 100 档分批生产，每档生成一个 job；
4. 条目状态 `pending / producing / done / failed`，去重靠状态位；
5. 生产结束可关闭批次（`closed`），也可提前关闭。

批次是独立实体：`web-data/batches/<id>.json`；历史页按 `batch_ref` 聚合，批次删除后任务落回「未分组」。

### 7.3 并发与线程

- 每个 job 一个线程池，`max_concurrency=100`；
- 4 个大批量 job 最多约 400 线程，但只有 100 个能拿到在飞名额；
- 线程多不等于云端并发大，真正限制是“在飞 + 额度”。

## 8. 监控与成本

| 能力       | 位置/接口                                        |
| -------- | -------------------------------------------- |
| 账户用量     | 管理 → 账户用量；`GET /api/admin/usage`             |
| 逐条明细     | 点账户展开；`GET /api/admin/accounts/{owner}/work` |
| 导出 CSV   | 同页「导出 CSV」；`.../work.csv`                    |
| 按账户筛选    | 任务/批次/历史均支持 `scope=all&owner=`               |
| 单 job 报表 | `GET /api/jobs/{id}/report.csv`              |

**金额算法**：`计费秒 × 单价`。计费秒来自云端 `usage`；单价取 `wan.price_per_second`，为 null 时用公开价目表兜底（480P 0.3 / 720P 0.6 / 1080P 1.2 元/秒）。

**历史任务回算**：早期任务生成时单价为 null，记录里没有金额；读取时按当前单价回算，标记 `cost_source=derived`，CSV 的「金额来源」列区分「实测 / 回算」。回算不修改任务文件。

## 12. 已知限制与风险

| 风险       | 说明                                                    | 应对                                |
| -------- | ----------------------------------------------------- | --------------------------------- |
| 额度是否合并   | 官方写“创建 300 RPM、轮询 20 RPS”分开；若实际合并计入 300 RPM，15 RPS 会超 | 观察日志 `[限流]`，出现就把 `query_rps` 降到 5 |
| 4 账户同时跑  | 在飞 100 只够 2 人各 50；4 人各 50 需 200                       | 改 `max_inflight=200`（15 秒轮询仍安全）   |
| 金额为估算    | 单价未填实际合同价                                             | 填 `price_per_second` 后与账单对齐       |
| 快速通道上限   | 全局 4 个小 job、每人 1 个                                    | 超出时排队，但不排在大批量后面                   |
| 线程规模     | 4 个百条 job + 4 个小 job 约 400+ 线程                        | 一般 50 条批量约 200 线程，正常范围            |
| 单 Key 共用 | 无法按 Key 拆账单，额度也只有一份                                   | 本地台账按账户拆分；控制台只做总额对账               |
| 服务托管     | 当前由 WorkBuddy 后台任务托管                                  | 关闭后双击 `启动网页服务.bat`                |

## 13. 运维手册

### 启动 / 重启

1. 关闭旧服务窗口（或结束对应 python 进程）；
2. 双击 `启动网页服务.bat`，或在项目目录执行 `python run_web.py`；
3. **等 8–10 秒**再访问：服务要先读配置与模板清单，端口绑定有数秒空窗；
4. 确认只有一个进程在监听：

```bash
netstat -ano | findstr :8765
curl http://127.0.0.1:8765/healthz
```

### 配置备份

| 文件                   | 备份                              |
| -------------------- | ------------------------------- |
| `server/config.json` | `config.json.bak-20261102-0941` |
| `server/web.json`    | `web.json.bak-20261102-0933`    |

### 常见现象

| 现象                | 原因                                          | 处理                                  |
| ----------------- | ------------------------------------------- | ----------------------------------- |
| 任务“正在生成”但 0/N、条目空 | 在飞名额被别的任务占满，或快速通道池满                         | 等名额释放；看管理端 `active`                 |
| 日志出现 `[限流]`       | 触发官方 429                                    | 降低 `query_rps` 或 `poll_interval`，重启 |
| 花费显示 0 或空         | 单价 null 且无计费秒                               | 填 `price_per_second`；确认任务已成功        |
| 第三个账户提交后排队        | `max_active_jobs=4` 或 `max_inflight=100` 已满 | 按实际人数调整并重启                          |
